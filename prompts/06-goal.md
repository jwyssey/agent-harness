# 06 구현 goal

- **언제**: 마일스톤마다. 완료 조건이 검사로 정해지는 묶음에만 쓴다("전부 만들어"는 쓰지 않는다).
- **먼저 손으로**: 이유 칸. 담당자 답 · RESULTS.md 행 · 가정 중 무엇 때문에 이 일을 하는지.
- **도는 동안**: `git diff --stat` → 핵심 함수 읽기, PLAN · DECISIONS 정리, 담당자 질문.

```
/goal 목표: ___ (마일스톤 N)
이유: ___ (담당자 답 · RESULTS.md 행 · 가정 중 무엇 때문에 이걸 하나)
완료 조건: ① ./check.sh 통과 ② PLAN.md 5번의 검증 명령 결과를 RESULTS.md에 한 행 추가
③ ARCHITECTURE.md의 의존성 · 상태 소유 · 요청 흐름을 실제 파일:함수로 갱신
범위: ___ 만. 고정한 평가(eval/ · 분할 · 고정 사례)는 고치지 않는다. 기존 테스트는 약하게 만들지 않고, 요구 때문에 고친 테스트는 이유를 보고한다. 상태 변경은 ___ 모듈에서만.
새 패키지가 필요하면 이유를 알리고 설치해(과제 문서가 막으면 설치하지 말고 알려 줘). 요구 충족에 필요한 입력 검증 · 오류 처리는 넣고, 범위를 늘리는 기능 · 추상화는 제안만 해.
완료 조건을 모두 확인한 뒤: 요구 항목별 구현 위치 / 확인한 명령과 결과 / 미구현을 표로 보고하고 이번 위임을 끝내.
```

- **v0** 의 완료 조건에는 "예시 입력 하나가 과제가 요구한 산출물 형식(화면 · CLI · API · 보고서)으로 끝까지 나온다"를 넣는다. 화면을 만드는 과제일 때만 "성과 화면이 RESULTS.md 의 값을 표시한다"를 더한다.
- **개선** goal 은 가설 하나만: "___ (현장 요인) 때문에 ___ 가 틀린다 → ___ 하면 현장 KPI가 오른다". 모델을 바꾸기 전에 현장 요인 반영을 먼저 의심한다.
- 일반 지시도 "X 해"가 아니라 "Y 때문에 X 해"로 쓴다.
