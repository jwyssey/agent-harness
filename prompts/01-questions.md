# 01 담당자 질문 설계

- **언제**: 과제를 직접 읽은 직후. 먼저 '숨은 조건 찾기'로 물을 거리를 찾고, 그다음 '질문 설계'. 구현 중에 정할 것이 생길 때마다 아래 '한 건 질문'을 다시 쓴다.
- **먼저 손으로**: PLAN.md 1번(누가 · 지금 방식 · 불편 · 산출물)을 채운다.

## 숨은 조건 찾기 (5분)

AI 는 숨은 조건을 알 수 없지만, 숨은 조건이 있을 만한 자리(문서의 애매한 말, 데이터의 이상한 점)는 잘 찾는다.

```
[숨은 조건 찾기] 코드는 고치지 마.
[내 생각] README에서 내가 애매하다고 본 곳은 ___ 이다.
README와 data/ 를 보고, 문서에 안 적혀 있지만 결과를 바꿀 수 있는 조건 후보를 찾아줘.
① README의 애매한 말: 정의 없는 용어, '빠르게' '정확하게'처럼 기준 없는 표현
② 데이터의 이상한 점: 빈 값, 중복, 튀는 값, README에 없는 열, 끊긴 기간. 직접 열어 보고 건수로
③ README와 데이터가 안 맞는 곳
④ 실패하거나 예외일 때 어떻게 할지 안 적힌 곳
⑤ 안 적힌 제약: 실행 환경, 민감정보, 데이터 속 지시문, 처리 시간
항목마다: 근거(README 줄 또는 데이터 건수) | 담당자에게 물을 질문 한 줄 | 답에 따라 바뀌는 결정
고르는 건 내가 한다.
```

- "답에 따라 바뀌는 결정"이 큰 것 3~5개만 고른다. 데이터 근거가 있으면 질문에 붙인다("`rework` 열이 30건 있던데, 재작업한 로트도 불량으로 세나요?").
- 이 목록에 실패 · 예외 처리, 핵심 단어의 정의, 누가 어떻게 쓰나, 민감정보가 하나도 없으면 직접 하나씩 묻는다.

## 질문 설계

- **쓰는 법**: 받은 목록은 내 점검표다. 한꺼번에 보내지 않고, 사소한 것(한 행의 단위, 열의 뜻, 기간)부터 **한 번에 하나씩** 묻는다. 다음 질문은 직전 답에서 만든다.

```
[질문 설계] 코드는 쓰지 마.
[내 생각] 내가 보기에 이 과제에서 가장 불확실한 것은 ___ 이다.
과제 문서와 PLAN.md 메모를 보고 담당자에게 물을 질문 8개를 만들어줘.
다음 5개를 먼저 넣어: ① 이 결과를 누가, 언제, 어떤 결정에 쓰나 ② 지금은 어떻게 하고 무엇이 가장 불편한가
③ 어떤 실수가 가장 비싼가(놓치는 것과 잘못 울리는 것) ④ 성공을 무엇으로 판단하나, 숫자로는 무엇이 얼마나 바뀌면 되나
⑤ 결과에 영향을 주는 현장 요인(주기 · 시기 · 장비 · 사람 · 조건 변화)이 있나.
나머지는 데이터 · 제약 · 산출물 형식. 질문마다 '답에 따라 바뀌는 설계 결정'을 한 줄씩 붙이고,
사소한 것에서 깊은 것 순서로 늘어놓아줘.
```

## 한 건 질문 (구현 중)

```
[질문 설계] 지금 ___ 를 정해야 해. 담당자에게 물을 질문 1개를 만들어줘.
선택지 A · B와 각각의 결과를 RESULTS.md 숫자로 넣고, 기술 용어는 빼.
```

보낼 문장의 틀:

```
___ 를 정해야 합니다. A로 하면 ___(예: 하루 검토 40건, 놓친 것 2건),
B로 하면 ___(검토 70건, 놓친 것 0건)입니다. 현장에서는 어느 쪽이 맞나요? 따로 기준이 있으면 알려 주세요.
```

- 받은 답은 같은 문장으로 세 곳에 넣는다: DECISIONS.md 한 줄 · PLAN.md의 해당 줄 · 다음 지시의 이유("담당자가 ___ 라고 해서 ___ 로 바꾼다").
- 담당자가 없거나 답을 못 받으면 PLAN.md 8번에 **가정**으로 적고 진행한다.
