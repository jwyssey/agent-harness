상황별 기법은 [PLAYBOOK.md](PLAYBOOK.md) 에 있다. 이 문서는 **언제 무엇을 부르고 무엇을 남기는지**에 집중한다.

## 과제 (가상 설정)

> 품질팀은 두 가지를 원한다.
> **A.** 공정 조건 · 계측 변수 36개로 제품 품질 Y 를 미리 예측하고 싶다. Y 가 있는 데이터는 47건뿐이고, 11건은 예측해서 제출한다.
> **B.** 센서 474개로 웨이퍼 불량을 미리 골라내고 싶다. 라벨이 있는 1367장 중 불량은 80장 남짓이다. 200장은 예측해서 제출한다.

데이터: `python3 make_data.py <워크스페이스>/data` 로 같은 모양의 합성 데이터를 만든다. 실제 공개 데이터로 B 를 연습하려면 UCI 의 SECOM 데이터(590 센서, pass/fail)가 비슷한 모양이다.

```

담당자: 웨이퍼 한 장입니다. 로트 정보는 이번 데이터에 없습니다.

담당자: 놓치면 고객 불량이라 훨씬 비쌉니다. 다만 재검사도 하루 150장이 한계예요.

받은 답은 모아서 Codex 에 옮겨 적게 한다. "이 답으로 바뀐 것" 칸은 내가 부른다.

| 10:00 | 비싼 실수       | 놓침이 훨씬 비쌈, 재검사 하루 150장 | 가드레일 = 놓친 불량 수, 임계값은 상한 안에서 |
```

## 3. KPI 사슬과 확인 (10:00–10:20)

`prompts/02` 의 표에서 내가 고른다. 예:

| | 현장 KPI | 모델 지표 | 가드레일 |

`$grilling PLAN.md 목표·범위에서 아직 안 정한 것 중 중요한 것 3개만 물어봐. 3개 끝나면 멈춰.` 예상 질문과 내 답:

- "B 의 임계값을 F1 최대로 정할까요?" → 아니. 담당자가 놓침이 더 비싸다고 했다. 재검사 상한(하루 150장 비율) 안에서 놓침이 가장 적은 지점으로.
- "A 의 중복 행은?" → 학습 구간에서 하나 지운다. 제출 대상은 건드리지 않는다.

## 5. 검증 고정 + v0 (10:30–12:15, goal 하나)

```
/goal 목표: 검증 방법을 고정하고 A · B 의 v0 까지 완주한다
이유: 담당자 확인(10:15, 확정) "놓침이 더 비싸고 재검사는 하루 150장이 한계"
순서: ① eval/run.py 를 만든다. A 는 RepeatedKFold(5-fold × 5회, seed 고정)로 RMSE 평균 · 최소 · 최대,
        B 는 StratifiedKFold(5, seed 고정) OOF 로 AP 와 '재검사 상한 안에서 놓친 불량 / 전체 불량'.
        전처리(스케일링 · 원-핫 · 열 정리)는 파이프라인 안에서 학습 fold 에만 fit 한다.
        `python3 eval/run.py --quick` 을 PLAN.md 5번 '검증 명령:' 에 적고 커밋한 뒤 해시를 'eval 고정 커밋:' 에 적는다
      ② v0: A 는 평균 → Ridge · ElasticNet → CatBoost(얕게), B 는 전부 정상 → 로지스틱(class_weight) → LightGBM(scale_pos_weight).
        각 결과를 RESULTS.md 에 한 행씩, 제출 대상 예측을 submit/A.csv · submit/B.csv 로
완료 조건: PLAN.md 에 고정 커밋 해시 · ./check.sh OK · RESULTS.md 에 A · B 각 3행 · ARCHITECTURE.md 갱신
범위: eval/ · src/ · submit/ 만. 고정한 평가는 ①의 커밋 뒤로 고치지 않는다. 하이퍼파라미터 탐색은 모델당 5분 안.
v0 완료 조건을 모두 확인한 뒤 표로 보고하고 이번 위임을 끝내. 개선은 시작하지 마.
```

도는 동안 나는 `git diff --stat` 을 보고 `eval/run.py` 의 분할 부분을 직접 읽는다. 전처리가 fold 밖에 있지 않은지가 핵심이다.

`RESULTS.md` 예(숫자는 예):
```
| 11:40 | a1b2c3d | A 평균 예측      | RMSE 0.21 (0.17~0.26) | ... | 기준 |
| 11:45 | a1b2c3d | A Ridge          | RMSE 0.12 (0.09~0.16) | ... | 개선 |
| 11:55 | c4d5e6f | A CatBoost 얕게  | RMSE 0.10 (0.07~0.15) | ... | 차이 작음(범위 겹침) |
| 12:00 | c4d5e6f | B LightGBM       | AP 0.24, 놓친 불량 52/80 (재검사 150장 상한) | ... | 개선 |
```
A 의 Ridge 와 CatBoost 처럼 범위가 겹치면 "개선"이라고 쓰지 않는다. 설명하기 쉬운 쪽을 고르고 그 이유를 `DECISIONS.md` 에 적는다.

| 질문 | 답의 순서 |
|---|---|
| 47건으로 낸 숫자를 믿을 수 있나 | 반복 CV 25번의 평균과 범위 → 범위가 겹치는 비교는 개선이라 하지 않았다 → 더 쌓이면 다시 잰다 |

| 왜 정확도가 아니라 AP · 놓친 수인가 | 전부 정상이라고 해도 94% → 담당자가 놓침이 비싸다고 했다 → 재검사 상한 안에서 놓친 수로 판정 |
| SMOTE 같은 합성은 왜 안 했나 | 센서 사이 관계를 모르는 채 합성하면 없는 패턴을 넣을 수 있다 → class weight 와 임계값으로 대신했다 |
| 실패하면 | 로트 정보가 없어 같은 로트가 학습 · 평가에 섞였을 수 있다 → 실제 적용 전 로트 단위 재검증이 필요하다 |

## 이 과제에서 흔한 함정

- **작은 n 에서 큰 탐색.** 47건에 수백 번 하이퍼파라미터를 탐색하면 검증 점수에 과적합되고 시간도 쓴다. 기본값 + 규제 세기 몇 개, 모델당 5분.
- **Nested CV 를 처음부터.** 정확하지만 무겁다. v0 은 반복 CV, Nested CV 는 개선 단계에서 모델 선택이 정말 쟁점일 때만.
- **임계값을 고른 데이터로 성능을 보고.** 같은 OOF 로 고르고 재면 낙관적이다. 그렇게 했다면 한계에 적는다.
- **약한 모델까지 섞은 앙상블.** 평균이 오히려 떨어진다.
- **라벨이 빈 행을 학습에 섞음.** 제출 대상(Y 가 빈 행)은 분할 전에 따로 뗀다.
