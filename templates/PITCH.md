# PITCH (3분 기준 — 주어진 시간에 맞춰 줄인다)

| 시간 | 내용 | 말의 뼈대 |
|---|---|---|
| 0:00–0:20 | 현장 문제 | 현재 ___ 담당자는 ___ 때문에 매번 ___ 를 판단해야 합니다. |
| 0:20–0:40 | 고른 목표와 제약 | 담당자에게 확인한 가장 비싼 실수는 ___ 여서, ___ 를 유지하면서 ___ 를 줄이는 문제로 정했습니다. |
| 0:40–1:10 | 화면 시연 | 예시 입력 하나로 대상 확인 → 판정 근거 → 다음 행동까지. 기능 목록은 말하지 않는다. |
| 1:10–1:55 | 현행 대비 결과 | 같은 평가 구간에서 현행은 ___, 제안은 ___ 였습니다. 놓친 사례는 ___/___ 입니다. 시간 절감 ___ 는 ___ 를 가정한 추정입니다. |
| 1:55–2:30 | 검증과 내 판단 | 분할 · 누수 점검 · 최종 확인을 짧게. 내가 직접 바꾼 결정 하나. |
| 2:30–3:00 | 한계와 다음 단계 | 아직 ___ 는 확인하지 못했습니다. 다음에는 ___ 조건에서 병행 검증하고, ___ 기준을 넘으면 적용하겠습니다. |

## 숫자 3개 (RESULTS.md에서 그대로)
1. 현행 대비 현장 KPI:
2. 가장 중요한 가드레일:
3. 표본 수(전체 / 양성):

## 받을 만한 질문과 답의 뼈대
| 질문 | 답의 순서 | 근거 위치 |
|---|---|---|
| 이 지표가 좋아지면 현장 성과도 좋아지나 | 담당자 기준 → 바뀌는 결정 → 잰 숫자 → 환산 가정 → 아직 못 보인 것 |  |
| 누수나 평가셋 과적합은 없나 | 분할 단위와 이유 → 전처리는 학습 구간에서만 → 개발 검증에서 선택 → 최종 확인. 희귀 사건은 건수 / 분모 |  |
| 모듈 의존과 상태 변경은 누가 하나 | 입력부터 결과까지 함수 순서 → 임시 상태와 영속 데이터 구분 → 변경 책임 → 이 구조를 고른 이유 |  |
| 조건이 바뀌거나 모델이 실패하면 | 감지 조건 → 구현된 동작 → 화면 표시 → 보장 못 하는 범위 |  |
| AI 제안 중 무엇을 직접 판단했나 | AI 제안 A → 내 기준 → 고른 B와 버린 이유 → 결과 · 코드 위치 |  |

답은 **지금 구현된 사실 → 이유 → 한계와 다음 확인** 순서. 질문의 전제가 구현과 다르면 그 차이부터 말한다.
